# Here now, and practising together

*Plan begun 2026-10-12; revised 2026-10-13 after Tam chose Django Channels and Redis,
starting with presence and a shared practice room with a synchronized timer. This revision
replaces the polling/SQLite-only proposal from Claude session

## The decision

Extend `~/code/webframework`. Keep its Django/DRF backend, React/TypeScript/Vite frontend,
accounts, session authentication, permissions and existing background-task system. Add
Channels, an ASGI server and Redis. Use Postgres for the wholy.sh instance's durable data.
Build reusable presence and practice apps in the kit; keep wholy.sh's reading page and its
small presence client in this repository.

The first delivery is a public active-visitor count and private new/returning statistics.
The second is a room where two or more signed-in participants see who is present and follow
one host-controlled timer. Both use the same realtime infrastructure. The first completed
vertical slice must survive reconnects, multiple server processes and a server restart.

Tam chose the stack and these two features. The following are implementation defaults:
signed-in room participants, host-only controls, unlisted invitation links, a separate
wholy.sh deployment, and `app.wholy.sh` for the application. They make the first release
concrete without reopening the stack decision. Hosting provider and budget remain to be
settled before deployment; local implementation does not depend on that choice.

## Deployment and origin boundaries

Target layout:

```text
wholy.sh / vi/             existing static reading page
  └─ public presence      wss://app.wholy.sh/ws/presence/

app.wholy.sh              kit's React app, Django HTTP API and WebSockets
  ├─ /auth/              existing Django session login
  ├─ /api/practice/      room creation, invitations, joining, snapshots
  ├─ /ws/practice/       room events and timer commands
  ├─ Postgres            users, room membership, timer state, visitor statistics
  └─ Redis               ephemeral presence, channel layer, shared limits
```

Serve the room app, API and room sockets on the same origin, with secure host-only session
cookies. The public presence socket accepts an explicit allowlist of reading-page origins;
it grants no access to accounts, member lists or timer controls. A CORS setting alone does
not protect WebSocket handshakes: use `OriginValidator` on socket routes. Missing or
unapproved browser origins fail closed in production; local origins are explicit settings.

Do not share the existing webframework/wut.sh production database. Shared kit code does not
require shared users, secrets or deployment cadence. Keep domain names, origins, feature
flags and instance prefixes configurable; no wholy.sh constants in reusable Python apps.

Provide a local Compose setup for Postgres and Redis, a Daphne development command, and a
Vite WebSocket proxy. On a VPS, Caddy or nginx terminates TLS and proxies upgrades to
Daphne; Redis and Postgres remain on the private network. On Fly, add an explicit wholy.sh
configuration rather than using the reference root `fly.toml`; keep an instance available
for active rooms and test idle timeout/keepalive behavior through the actual proxy.

The old roughly $4/month estimate was for one small SQLite machine. It is not a budget for
this stack. Size Django, Redis and Postgres after a pilot load test. A single VPS is an
acceptable initial failure domain if its limitations and off-machine backups are explicit;
managed or separate database services remain an operational choice. Test backup restoration
before storing production practice history. Production resource creation and DNS changes
belong to a subsequent deployment task, not this planning update.

## Phase 1: public presence and private visitor statistics

### Define what is being counted

An active reading-page visitor has at least one visible page with an unexpired presence
lease. Use a random browser ID in localStorage, as Tam originally requested. Deduplicate
ordinary tabs using that ID; sockets and tabs are separate connection IDs. The result is an
estimate of browsers, not people. Clearing storage or using another browser creates another
visitor. No IP fingerprinting and no public visitor identifiers or roster.

Do not assume localStorage crosses origins. `wholy.sh` and `/vi/` share one reading-page
scope; `app.wholy.sh` has its own app scope. Do not sum their anonymous counts and label the
result unique people. Authenticated room presence deduplicates by user ID within the room.

Honor the previous plan's DNT/GPC preference: do not read or write the persistent visitor ID
or include that connection in visit statistics when either signal is enabled. Use an
ephemeral page identity for functional presence. Those pages cannot be deduplicated across
tabs; disclose this limitation in the count's definition. Storage failures use the same
ephemeral behavior. A visitor ID is only an analytics key, never an authentication token.

### Leases, failure and client lifecycle

- The browser sends a validated `hello` after connecting, then an application heartbeat
  every 20 seconds while visible. The server grants a 60-second lease, using server time.
- A connection has a server-assigned ID. Redis tracks connections and their visitor key
  under a configured site scope. Disconnecting one tab cannot remove another tab's lease.
- Use bounded Redis structures and atomic update/prune/count operations, for example a
  sorted set of connection expiries plus connection-to-visitor metadata. Expired leases and
  their metadata are pruned together. Count distinct live visitor keys; no SQL heartbeat
  writes. Channels groups are delivery groups, not an enumerable presence database.
- Publish count changes on joins, leaves and pruning. Every heartbeat reply also includes
  the current count; expiry must become observable without requiring a new visitor to join.
  Refresh Channels group membership on renewal as well as connection.
- Hidden pages report inactivity and stop renewing. `pagehide`/close are best effort; the
  lease bounds stale presence when a phone sleeps, crashes or loses the network. On return,
  reconnect or renew and obtain a fresh snapshot. Socket connectivity alone is not activity.
- On disconnect, offline state, Redis failure or no server reply within 60 seconds, clear
  the public count. Reconnect with jittered exponential backoff, capped at 30 seconds;
  reset after a healthy exchange. Close sockets on component cleanup/navigation.
- Bound message sizes, heartbeat rates, connection counts and per-scope cardinality. Apply
  shared Redis limits with allowances for multiple people behind one NAT; an origin check
  does not make anonymous counts resistant to forged clients or bots.

### New and returning visitors

Keep statistics separate from liveness. On the first acknowledged visible hello of a local
day, record an idempotent visit using a server-side keyed hash of the browser ID and scope.
Do not log raw IDs. A unique `(scope, visitor_key, day)` prevents reloads, tabs and retries
from inflating the day's total. Repeat heartbeats do not write visit records.

Proposed Postgres models:

| Model | Purpose |
|---|---|
| `Visitor` | Unique scope/key, first-seen and last-seen dates. |
| `DailyVisit` | One visitor per scope/day; classification fixed as new or returning for that day. |
| `DailyPresenceSummary` | Per-scope daily peak and aggregates; peak updates are coalesced, not written on every heartbeat. |

Use the configured timezone (`America/Toronto` for wholy.sh), with UTC timestamps underneath.
New means first observed today; returning means first observed on an earlier day. Handle
concurrent first sightings transactionally. A page that stays open over midnight must
register the next day's visit without reconnecting. Redis may cache acknowledgement of
that visit; the database uniqueness constraint remains the final deduplication rule.

Default retention: 400 days for daily data and 400 days of inactivity for visitor records;
a scheduled management command prunes independently of someone opening the stats page.
After retention or storage loss, a browser may count as new again. No lifetime-unique claim.
Keep stats private behind a dedicated read-only bearer credential initially, supplied in
an Authorization header and never embedded in the public page. Account-protected admin
reporting can be added later. Avoid exporting pseudonymous per-visitor rows through this API.

### Reading-page integration

Keep the quiet footer line from the original plan: `7 here now`, shown only at counts of
two or more, with reserved height, no live-region announcements, no print output and no
motion under reduced-motion preferences. Vietnamese copy must be generated through the

new browser-count definition.

Replace the earlier date-only privacy note. It must explain the random browser identifier,

Connect only on the configured production hostname or an explicit development override.
Ordinary checkouts, simulations and existing performance checks start no network request,

## Phase 2: one shared practice room

### The user flow

1. A signed-in user creates an unlisted room, chooses a duration (default 10 minutes;
   allowed range 1–120 minutes), and receives an invitation link.
2. A participant opens the link, signs in through the existing kit flow, and explicitly
   joins. Joining grants room membership; knowing or guessing a room UUID alone does not.
3. Everyone sees the room title, connected participants and the same timer state. The host
   can start, pause, resume, reset and close the room. Other participants can leave.
4. The host leaving or losing the network does not pause the timer or transfer control.
   On return, the host receives the current state. Host handoff is a later feature.
5. At zero, the timer shows completion. There is no automatic next practice and no
   attendance, virtue or performance score. Reset prepares a new run and increments its ID.

Use a high-entropy invitation secret, store its hash, and allow rotation/revocation. Exchange
the secret through a CSRF-protected join POST. Avoid putting it into analytics, referrers or
WebSocket URLs; an invitation URL fragment can carry it until that exchange. Room sockets
authenticate with the existing Django session, then check persisted membership. Membership
revocation and room closure also invalidate existing connections, with heartbeat rechecks
as a backstop if the immediate revocation event is lost. No anonymous room access in v1.

Participant presence is distinct from page visibility: an authenticated joined room remains
present while its connection renews, even if backgrounded briefly; a sleeping phone can lose
its lease. Show connection state without treating lost presence as abandoning the practice.
The timer continues regardless. Deduplicate multiple tabs for a member in the room roster.

### Durable room state

`practice` owns three initial models:

- `PracticeRoom`: UUID, creator/host, title, invitation hash, closed-at timestamp, configured
  duration, run ID, status, remaining milliseconds when paused/ready, deadline when running,
  monotonic integer revision, and created/updated timestamps.
- `RoomMembership`: room/user unique pair, joined-at and revoked-at timestamps. Host status
  is checked against the room's host; do not trust a role sent by the browser.
- `RoomCommand`: room/actor/request UUID unique key, payload hash, accepted revision and
  outcome, for retry deduplication. Retain for the room's lifetime in v1; deleting a room
  deletes its command records. No unbounded event log of heartbeat or countdown ticks.

All timer mutations go through one transactional service: lock the room row, check
membership and host authority, recognize duplicate requests, validate the expected revision
and state transition, update durable state, save the command result, then commit. Two
workers handling competing commands must not create competing timers. Check idempotency
before rejecting the old revision on a retry; reuse of a request ID with another payload
is an error. Broadcast only after commit.

Redis carries presence and notifications; it is not the only record of a running practice.
A database restart or restore has normal durability limits; a Django or Redis restart
must not reset the timer. Do not queue room controls through the kit's existing offline
post outbox: a stale start or pause must not execute unexpectedly when a phone reconnects.

### Timer state machine and clock

| Command | Allowed state | Result |
|---|---|---|
| Start | ready | running, deadline = server now + prepared duration |
| Pause | running before deadline | paused, remaining = max(0, deadline − server now), deadline cleared |
| Resume | paused | running, deadline = server now + saved remaining |
| Reset | ready/running/paused/completed | ready, new run ID, configured duration restored, deadline cleared |
| Close | any open state | room closed; later commands and joins rejected |

An elapsed running deadline means completed even if no process was alive at that instant.
On the next snapshot or command, normalize this state transactionally and increment the
revision once. A pause received after the deadline cannot resurrect time. Completion
rendering does not wait for this normalization. Resetting or changing duration is an
explicit host action; a reconnect never changes it.

Snapshots include `server_time`, `deadline`, `remaining_ms`, `status`, `revision`, `run_id`
and a sanitized member list. Clients estimate server clock offset from round-trip samples,
favor low-latency samples, and anchor elapsed rendering to a monotonic browser clock.
Recalibrate after wake, visibility changes, reconnects and periodic heartbeats. Never derive
remaining time by decrementing a counter once per second or trust the device's wall clock.

While connected, render the countdown locally from the authoritative deadline. Start,
pause, resume and reset are broadcast immediately; there is no per-second broadcast.
Disable host controls until a current snapshot is available. During an outage, show that
the connection is lost; a locally projected countdown may continue, but must be visibly
unconfirmed because another client might have changed the room. A reconnect replaces it
with the latest snapshot. Only show a successful command after server acknowledgement.

A common deadline is the v1 synchronization target. Sample-accurate bells, guaranteed
background audio on phones, audio/video calls and automatically sequenced practices are
outside this release. No scheduler is required just to make a deadline expire; later
server-side completion side effects will need idempotent scheduled work.

## Protocol and recovery

Use versioned JSON envelopes (`v: 1`, `type`) and UUID request IDs for commands. Send stable
error codes with human-readable UI messages, never Python tracebacks. Keep the public
presence consumer and authenticated room consumer separate.

| Endpoint/event | Contract |
|---|---|
| `GET /presence/stats/?days=N` | Private aggregate statistics, bounded day range. |
| `WS /ws/presence/` | `hello`, `heartbeat`, `inactive`; replies contain count and server time, no roster. |
| `POST /api/practice/rooms/` | Authenticated, CSRF-protected room creation. |
| `POST /api/practice/rooms/<id>/join/` | CSRF-protected invitation exchange into membership. |
| `GET /api/practice/rooms/<id>/` | Authorized current snapshot, also used for recovery. |
| `POST .../<id>/leave/`, `POST .../<id>/invite/rotate/` | Membership leave and host-only invitation rotation. |
| `WS /ws/practice/rooms/<id>/` | Session-authenticated, membership-authorized room connection. |
| `timer.command` | `request_id`, `expected_revision`, `action`, optional validated duration. |
| `command.result` | Request ID, accepted/rejected result and authoritative current snapshot. |
| `room.snapshot` | Full timer state and revision; initial join, mutations, explicit resync and every 20-second heartbeat response. |
| `room.presence` | Current authorized roster; its own sequence, independent of durable timer revision. |

Group broadcasts may be dropped. Joining subscribes before reading the snapshot; reconcile
any racing updates by revision. Clients ignore older timer revisions, request a snapshot
on a gap, and periodically refresh even when no gap is visible. Heartbeats carry a fresh
server time and state, not only an echo. This repairs a lost final pause/reset even if no
later command occurs. Presence has a separate sequence so it cannot hide timer changes.

If the database commit succeeds but the broadcast or acknowledgement is lost, retrying the
same request returns its stored outcome and a fresh snapshot. It never applies twice.
Handle post-commit publish failures as delivery failures, not as a rolled-back mutation.
For this snapshot-based v1, periodic reconciliation covers this gap; a durable event outbox
can be introduced when missed notifications or message history acquire their own meaning.

Rejoin delivery groups after Redis recovery, not just after browser reconnection. On Redis
failure mark room connections degraded and force a controlled reconnect/resubscribe path;
renewals repopulate leases. The server validates message sizes and schema, authenticates
connections, checks membership on commands and renewal, enforces host authority in the
transaction, and rate-limits join/command floods across workers.

Revalidate the Django session itself on commands and renewal, rather than trusting the
user object cached at the initial handshake. Reject expired or logged-out sessions and
remove their leases. Duration changes are accepted only as part of an explicit host reset
and obey the same revision and idempotency checks as every other timer command.

## Implementation sequence in the two repositories

Work from current repository instructions and existing changes when implementation starts.
Use isolated branches/worktrees as needed, with `codex/` branch prefixes. Do not assume the
older Claude worktree name or its recorded HEAD still applies. This plan does not create
commits; later commits follow the user's attribution helper and explicit staging rules.

1. **Kit infrastructure.** Update dependencies, `server/config/asgi.py`, settings,
   `server/start-prod.sh`, development commands and deployment examples. Add Postgres/Redis
   local services and CI services. Make realtime an explicit instance capability so existing
   kit users are not forced to configure Redis before unrelated features boot. Enabled
   production realtime must fail clearly if Redis is missing, with no in-memory fallback.
2. **Kit presence.** Add `server/apps/presence/` services, consumers, statistics models,
   migrations, retention command, private stats endpoint and tests. Publish the protocol and
   environment variables in the kit's documentation; update `.env.example`.
3. **Reading-page presence.** Add footer/client/privacy copy and generated Vietnamese output
   in this repo. Add deterministic browser checks with mocked WebSockets. The service stays
   disabled in ordinary local and regression-test runs.
4. **Kit practice backend.** Add `server/apps/practice/` models, transactional commands,
   invitations, membership, snapshot endpoints, consumers and Postgres concurrency tests.
   This is a generic timed room; it does not import wholy.sh's editorial taxonomy.
5. **Kit practice frontend.** Add a lazy route `/practice/rooms/:id` in `app/src/App.tsx`,
   room creation/join UI, room view, timer state reducer and clock helper. Use the existing
   auth/API utilities. Own connection cleanup explicitly; React development remounts must
   not leave duplicate sockets. Keep timer commands out of `lib/outbox.ts`.
6. **Integration and operations.** Exercise two server processes against the same Redis and
   Postgres, proxy upgrades, failure recovery and browser sleep. Add runbook, metrics, flags,
   dependency readiness checks and a rollback procedure. Preserve the existing cheap
   `/healthz/` liveness endpoint; readiness reports database/Redis inability separately.
7. **Staged rollout.** After the deployment target is chosen, deploy infrastructure and kit
   presence, verify it, then enable the public footer. Enable rooms for an initial invited
   group before adding a prominent reading-page entry. Disabling rooms or the footer must
   not require destructive schema rollback or remove users' durable data.

Keep the implementation spec and operating details with the kit under
`docs/plans/2026-10-13-presence-and-practice.md` when code work begins; this document remains
the cross-repository plan and wholy.sh integration record. Do not maintain two independently
edited protocol definitions: the kit becomes the protocol's source once implemented.

These are implementation gates, not tests claimed to have run during planning.

| Area | Required evidence |
|---|---|
| Existing kit | `just verify`, existing browser suite, auth/CSRF, uploads, private media, HTTP routes and background tasks still work under ASGI. `just verify` alone does not run Playwright. |
| Real infrastructure | Integration tests use real Redis and Postgres. Two Daphne processes share a room; no correctness claim based only on in-memory Channels or SQLite. |
| Presence | Two tabs with one browser ID count once; a separate browser counts separately; closing one tab keeps the other. Hidden/crashed pages expire within the lease window plus the next observation. |

| Clock behavior | In a controlled low-latency test, displayed remaining times differ by at most 250ms after synchronization. Test device clocks skewed by ±5 minutes and delayed heartbeat samples; report measured limits under added jitter instead of claiming universal simultaneity. |

## Remaining decisions and scope

- **Before deployment:** pick Fly or a VPS, the actual machine/service budget, DNS hostname
  and production credentials. This does not block implementing or testing either phase.
- **Before public release:** review truthful English/Vietnamese presence copy and retention
  disclosure; complete real-phone checks. Put concrete handoffs into `docs/open.md` as

managed realtime vendor, date-only visitor identity, SQL table of heartbeat writes, or
30-second polling as the primary live transport. A heartbeat remains necessary for leases,
clock sampling and recovery; it now travels through the live connection.
